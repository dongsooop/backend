# BlindDate

## 책임

익명 과팅의 참가자 배정, 대화 진행, 선택 접수, 상호 선택 판정과 결과 이벤트를 관리한다.
채팅방 생성과 이후 대화는 Chat 도메인에 위임한다.

## Terminology

- Session: 참가자가 함께 대화하고 선택하는 과팅 단위.
- Choice: 참가자가 한 번 제출하는 상대 선택.
- Match: 두 참가자가 서로 선택한 결과.
- Choice Period: 참가자 목록 전송 직전에 시작하는 10초 선택 접수 기간.

## 주요 흐름과 규칙

정원 충족 → 안내 및 대화 → 참가자 목록과 선택 접수 시작 → 접수 마감 →
접수된 선택 처리 완료 → 미매칭자에게 실패 이벤트 → 세션 종료.

상호 선택이 처리되면 채팅방을 생성하고 두 참가자에게 성공 이벤트를 전송한다.
일부 참가자의 매칭이 성공해도 성공 이벤트 처리를 마친 뒤 나머지 미매칭 참가자에게 실패 이벤트를 전송한다.
최종 결과 처리에서는 이미 매칭된 참가자를 실패 대상에서 제외한다.
선택 접수 시작 전과 마감 이후 요청은 무시한다.

## 선택 입력 검증과 오류 응답

선택자는 해당 세션 참가자여야 하며, 대상도 같은 세션에 등록된 다른 참가자여야 한다.
큐에서 선택을 처리할 때 참가자 저장소가 검증한 뒤 선택과 매칭 상태를 기록한다.
잘못된 선택은 최초 선택 기회를 소비하지 않으므로 이후 정상 선택을 제출할 수 있다.
진행 중 소켓 연결이 모두 끊겨도 세션에 남아 있는 참가자는 선택 대상이 될 수 있다.

선택 오류는 HTTP 응답 또는 연결을 종료하는 STOMP ERROR 프레임이 아니라,
`/topic/blinddate/session/{sessionId}/member/{memberId}/choice-error`에 JSON으로 전달한다.
클라이언트는 이 개인별 토픽을 구독해야 하며, 오류 이후에도 같은 연결로 정상 선택이 가능하다.
응답 필드는 `status`, `code`, `message`이다.

| 조건 | status | code |
| --- | --- | --- |
| 선택자가 해당 세션 참가자가 아님 | 403 | CHOICE_FORBIDDEN |
| null 대상 또는 자기 자신 선택 | 400 | INVALID_CHOICE |
| 해당 세션에 대상이 없음(미등록·다른 세션) | 404 | CHOICE_TARGET_NOT_FOUND |

선택자 권한, 대상 형식, 대상 참가 세션 순으로 검증한다.
선택 시작 전·마감 후의 요청은 기존 정책대로 무시한다.

## 동시성 및 마감 보장

`BlindDateEventQueue`는 입장·재접속·퇴장 등 참여 이벤트를 전역 단일 스레드 큐에서 처리한다.
Choice와 최종 결과 작업은 `sessionId`별 직렬 큐에서 처리하며, 같은 Session에서는 한 번에 하나만
실행한다. 서로 다른 Session은 5개의 공용 worker 범위에서 병렬로 실행한다.
접수 가능 여부 확인과 큐 삽입, 접수 차단과 최종 결과 작업 삽입은 같은 잠금을 사용한다.
잠금은 작업 제출에만 사용하며 채팅방 생성이나 이벤트 전송을 기다리는 동안 유지하지 않는다.
전체 참가 상태를 초기화할 때는 새 Choice 접수를 먼저 닫고, 이미 제출된 세션 작업의 완료를 기다린 뒤
참가 큐에서 저장소를 정리한다.

최종 결과 작업이 실행될 때는 앞서 접수된 선택의 채팅방 생성 및 성공 이벤트 발행이
반환된 상태이며 새 선택은 접수되지 않는다. 진행 건수를 별도로 관리하지 않는다.
실패 이벤트를 발행한 다음 `finally`에서 세션을 종료하므로 전송 예외에도 세션은 종료된다.

접수 시점은 서버가 접수 잠금 안에서 선택을 확인하는 시점이다.
경과 시간은 `System.nanoTime()`으로 비교한다. 마감 타이머가 지연되어도 기한 이후 요청은 받지 않는다.
클라이언트의 전송 시각과 네트워크 도착 시각을 보장하는 정책은 아니다.

## 제약과 실패 처리

상태와 큐는 프로세스 내부에 있다. 여러 서버가 같은 세션을 처리하는 구성은 지원하지 않는다.
느린 채팅방 생성은 같은 Session의 후속 처리만 지연시키며, 공용 worker가 모두 점유되면
다른 Session도 worker가 반환될 때까지 기다릴 수 있다.
선택 작업을 별도 비동기로 분리한다면 해당 작업의 완료를 기다리는 구조도 함께 필요하다.
성공 이벤트 발행 완료는 서버 전송 호출의 반환을 뜻하며 클라이언트 수신 확인을 뜻하지 않는다.
채팅방 생성 실패 보상과 이벤트 전송 재시도는 이 마감 정책의 범위에 포함하지 않는다.
