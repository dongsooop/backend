# Meal

> 관련 패키지: `src/main/java/com/dongsoop/dongsoop/meal/**`

## Responsibility

- 학교 홈페이지 "금주의 식단" 페이지를 크롤링해 이번 주·다음 주 학생식당 식단을 저장하고 앱에 내려준다.
- 식단 페이지의 공지사항(운영시간 변경 등)을 주 단위로 저장하고 식단과 함께 내려준다.
- 학생식당 가격표(식권 가격, 단품 메뉴별 가격)를 설정 파일로 관리하고 API 로 내려준다.

## Out of Scope

- 교외 식당 정보 → `restaurant` 도메인
- 식단 화면 노출 방식과 캐시 정책 → 앱

## Terminology

### Korean Menu (한식)

- 의미: 식단 페이지의 "한식 메뉴" 행. 식권 한 장으로 먹는 정식.
- 코드: `MealType.KOREAN`, 응답 `koreanMenu`

### Special Menu (단품)

- 의미: 식단 페이지의 "단품 메뉴" 행. 덮밥·라면류·돈까스류 등 개별 가격으로 파는 메뉴.
- 코드: `MealType.SPECIAL`, 응답 `specialMenu`
- 혼동하면 안 되는 용어: 학교 페이지가 예전에는 이 행을 "별미 메뉴"라고 표기했다(2026-09 확인 시점에 "단품 메뉴"로 바뀌어 있었다). enum 이름과 응답 필드명은 앱·DB 호환을 위해 `SPECIAL`/`specialMenu` 를 유지한다.

### Notice (공지)

- 의미: 식단 페이지 맨 아래 "공지사항" 행. 운영시간 단축 같은 식당 운영 안내.
- 코드: `MealNotice`, 응답 `notice`
- 혼동하면 안 되는 용어: 학교 공지사항(`notice` 도메인)과 다르다.

### Price Table (가격표)

- 의미: 식권 가격(`ticketPrice`)과 분류별 단품 메뉴 가격. 학교 페이지에는 없는 정보라 서버 설정으로 관리한다.
- 코드: `MealPriceProperties`(설정), `MealPriceResponse`(응답)

## Main Flow

```text
매주 토 09:00 (실패 시 일 09:00, 월 매시 30분 재시도)
  ↓
학교 식단 페이지 2회 요청 (이번 주, 다음 주)
  ↓
MealParser: 날짜 범위 + 한식/단품 5일치 + 공지사항
  ↓
meal 테이블: 해당 주 삭제 후 저장 / meal_notice 테이블: 주 단위 덮어쓰기
  ↓
GET /meal/current → 월~금 한식·단품 + notice
GET /meal/prices  → application.yml 의 meal.prices
```

## Domain Rules

- 식단은 월~금 5일, 타입마다 한 줄씩 항상 채운다. 페이지에 없거나 `-` 이면 "식단 정보 없음".
- 파서는 "단품 메뉴" 행을 먼저 찾고 없으면 "별미 메뉴" 행을 받는다. 학교가 표기를 되돌려도 동작해야 한다.
- 공지는 그 주 페이지에 없으면 저장된 것도 지운다. 학교가 공지를 내렸는데 앱에 남아 있으면 안 된다.
- 가격표 값은 `application.yml` 의 `meal.prices` 가 유일한 원본이다. `days` 가 비어 있으면 매일 판매, 값이 있으면 그 요일에만 판다(월~금 한글 한 글자, 식단 응답의 요일 표기와 같다).

## Decisions

### 가격표를 DB 가 아니라 설정 파일에 둔다

#### 선택

`application.yml` 의 `meal.prices` 에 분류·메뉴·가격·곱빼기 가격·판매 요일을 적고, `@ConfigurationProperties` 로 바인딩해 `GET /meal/prices` 로 내려준다. 응답은 하루 캐시.

#### 이유

학교 페이지에 가격이 없어 크롤링할 수 없고, 값은 학기에 한 번 바뀔까 말까 한 정보다. 관리자 API·테이블·화면을 만드는 비용보다 값 바꾸고 재배포하는 편이 싸다.

#### 영향 / Trade-offs

- 가격이 바뀌면 yml 수정 후 배포해야 한다. `MealPricePropertiesTest` 가 yml 구조를 검증하므로 값을 고칠 때 같이 맞춘다.
- 자주 바뀌거나 운영자가 직접 고치게 되면 그때 DB + 관리자 API 로 옮긴다.

### 공지를 식단 행이 아니라 별도 테이블에 둔다

#### 선택

`meal_notice(week_start unique, content)` 에 주 단위로 저장하고 크롤링 때마다 덮어쓴다.

#### 이유

공지는 날짜·타입 단위가 아니라 주 단위 정보라 `meal` 행에 넣으면 10번 중복된다. 세 번째 `MealType` 으로 넣으면 "이번 주 식단이 비었는지" 판단하는 쿼리들이 공지를 식단으로 오인한다.

#### 영향 / Trade-offs

- 테이블 하나가 늘고, 정리 스케줄(2주 지난 데이터 삭제)에 한 줄이 추가된다.

## Failure Handling

- 크롤링 실패는 로그만 남기고 스케줄러가 멈추지 않는다. 토·일·월 재시도로 보완한다.
- 파서는 표 구조가 어긋나도 예외를 던지지 않고 "식단 정보 없음"으로 채운다. 공지는 없는 것으로 처리한다.
- 학교 쪽 입력 오류(한식 칸에 단품 내용이 섞여 들어오는 등)는 그대로 내려준다. 서버에서 교정하지 않는다.

## Concurrency / Consistency

- 크롤링과 정리는 스케줄러 단일 스레드에서 트랜잭션 하나로 실행된다.
- 같은 주 식단은 삭제 후 저장, 공지는 `week_start` 유니크 키로 조회 후 갱신한다. 동시 크롤링은 가정하지 않는다.
