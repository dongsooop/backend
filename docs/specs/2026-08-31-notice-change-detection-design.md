# 공지 정정·삭제 감지 및 알림 — 설계 기획서

작성일: 2026-08-31
대상 레포: dongsooop/backend (pacu 브랜치 기준)
상태: 초안 — 사용자 검토 대기

---

## 1. 배경과 문제

동숲의 주력 기능은 학교 공지를 크롤링해 구독 학과·키워드 기준으로 푸시하는 것이다.
지금 크롤러는 **학과별 목록 페이지 1장을 읽고 "DB에 저장된 최신 글번호보다 큰 글"만** 골라 저장·발송한다
(`NoticeCrawl.parseNewNotice` → `noticeDetails.getId() > recentlyNoticeId`).
한 번 저장된 공지는 다시 보지 않으므로 다음 두 문제가 구조적으로 생긴다.

1. 학교가 공지를 **정정**(제목·본문·첨부 수정)해도 감지하지 못한다. 사용자는 처음 받은 알림 내용이 최신이라고 믿는다.
2. 학교가 공지를 **삭제**해도 우리 DB와 앱 공지 목록에는 그대로 남는다. 탭하면 학교 에러 페이지가 뜬다.

## 2. 목표 / 비목표

**목표**
- 이미 저장·발송한 공지의 정정과 삭제를 감지한다.
- 감지 시 원 공지와 같은 대상(학과 구독 기기, 회원은 키워드 필터)에게 "수정됨/삭제됨" 알림을 보낸다.
- 삭제된 공지를 앱 공지 목록·홈·검색에서 내린다(물리 삭제는 하지 않는다).
- 학교 서버에 과한 부하를 주지 않고, 오판(멀쩡한 공지를 삭제로 표시)을 구조적으로 막는다.

**비목표 (이번 범위 밖)**
- 공지 본문 자체를 우리 DB에 저장하거나 앱에서 본문을 렌더링하는 것.
- 변경 이력(diff) 화면. 이번에는 "바뀌었다/지워졌다" 사실과 시각만 남긴다.
- 알림 타입 신설이나 알림 설정 화면 변경. 기존 `NotificationType.NOTICE`를 재사용한다.
- Elasticsearch 색인 동기화 로직 변경(이 레포가 색인하지 않음, 4.5절 참고).

## 3. 현재 구조 (코드로 확인한 사실)

| 항목 | 현재 |
|---|---|
| 크롤 주기 | `NoticeSchedulerImpl.scheduled()` — 평일 08–19시 10분 간격, 학과 27개를 스레드 8개로 병렬 |
| 읽는 범위 | 학과별 목록 페이지 1장(15행). 상세 페이지는 열지 않는다 |
| 저장 모델 | `NoticeDetails(id=학교 글번호, writer, title, link, createdAt)` + `Notice(department, noticeDetails)` 다대다 매핑. 대학 공지(DEPT_1001)는 여러 학과에 같은 details가 매핑될 수 있음 |
| 신규 판정 | 학과별 `MAX(noticeDetails.id)`보다 큰 글번호만 신규 |
| 발송 | `NoticeNotificationImpl.send(Set<Notice>)` — 학과 구독 기기 조회 → 회원은 키워드 필터 후 알림함 저장+푸시, 비회원은 푸시만 |
| 목록 조회 | `NoticeRepository.findAllByDepartment / findAllByDepartmentIn`, 홈은 `NoticeRepositoryCustomImpl`의 쿼리 3개 |
| 검색 | Elasticsearch `BoardDocument(type=NOTICE)`. **이 레포는 색인을 쓰지 않는다** — 외부 파이프라인이 DB를 읽어 색인하는 구조 |
| 스키마 관리 | Flyway 없음, `ddl-auto: update`. 백필이 필요할 때만 `src/main/resources/migration/{PR번호}_*.sql`을 수동 실행 |
| 수동 트리거 | `POST /notice` (ADMIN) → `scheduled()` 직접 호출 |

## 4. 학교 사이트 조사 결과 (2026-08-31 실측)

설계의 핵심 제약이 여기서 나온다. 모두 `curl`로 직접 확인했다.

### 4.1 상세 페이지 마크업
대학 게시판(`/bbs/dmu/{board}/{id}/artclView.do`)과 학과 게시판(`/combBbs/dmu/{a}/{b}/{id}/view.do`) 모두 동일한 클래스 구조다.

| 선택자 | 내용 |
|---|---|
| `.view-sj` | 제목 (끝에 UI 텍스트 "단축URL복사"가 붙어 나옴 — 정규화 시 제거 필요) |
| `.view-info` | **글번호만 있다. 수정일·등록일이 없다** → 변경 감지는 내용 해시 비교로만 가능 |
| `.view-con` | 본문 |
| `.view-file` | 첨부파일명 목록 (없으면 "첨부파일이(가) 없습니다.") |

### 4.2 존재하지 않는 글번호의 응답
`/bbs/dmu/677/1/artclView.do` → **HTTP 200** + `<title>알림메세지</title>` 페이지, 본문에
"원하시는 페이지를 찾을 수가 없습니다." 문구. `.view-sj`, `.view-con` 없음.
→ **HTTP 상태 코드로는 삭제를 잡을 수 없다.** 본문 문구 또는 선택자 부재로 판정해야 한다.

### 4.3 글번호는 학교 전체 공용이다
목록 페이지의 글번호 사이 빈 번호(251651 등) 14개를 전부 열어 보니 **모두 다른 학과/게시판의 정상 글**이었고,
게시판 경로가 달라도 글번호만 맞으면 200으로 내용이 나온다(`/bbs/dmu/677/50000/…`이 분실물 게시판 글을 그대로 렌더링).
→ **"목록 페이지에서 사라짐"은 삭제의 근거가 될 수 없다.** 삭제는 반드시 상세 페이지를 직접 열어 판정한다.
→ 반대로 상세 URL은 게시판 경로와 무관하게 글번호만으로 열리므로, DB에 저장된 `link`를 그대로 써도 된다.

### 4.4 확인하지 못한 것 (검증 필요)
- **실제로 삭제된 글**의 응답 샘플을 확보하지 못했다(빈 번호가 전부 다른 게시판 글이었음).
  4.2의 "없는 번호" 응답과 동일하다고 가정하되, 배포 전 운영 DB에서 오래된 공지 몇 개를 열어보거나 첫 배포 후 로그로 확인한다.
  이 가정이 틀릴 경우를 대비해 삭제 판정은 "에러 문구 확인" 단일 조건 + 연속 N회 확인으로 보수적으로 둔다(5.3절).

## 5. 설계

### 5.1 데이터 모델 — `NoticeDetails`에 컬럼 5개 추가

| 컬럼 | 타입 | 의미 |
|---|---|---|
| `content_hash` | VARCHAR(64), nullable | 제목+본문+첨부명 정규화 후 SHA-256. null이면 아직 베이스라인을 못 잡은 상태 |
| `content_checked_at` | TIMESTAMP, nullable | 마지막으로 상세 페이지를 성공적으로 읽은 시각 |
| `modified_at` | TIMESTAMP, nullable | 마지막 변경 감지 시각. 앱에서 "수정됨" 표시에 쓸 수 있도록 `NoticeListResponse`에 노출 |
| `deleted_at` | TIMESTAMP, nullable | 삭제 확정 시각. null이면 살아 있는 공지 |
| `delete_suspect_count` | INT, default 0 | 삭제 후보로 연속 관측된 횟수(5.3절). 정상 응답을 받으면 0으로 리셋 |

- 모두 nullable/기본값이므로 `ddl-auto: update`로 컬럼이 자동 추가된다. **백필 SQL은 필요 없다.**
- 변경 이력 테이블은 만들지 않는다(비목표). 알림 본문에 "이전 제목"이 필요하면 감지 시점 메모리 값으로 충분하다.
- `Notice`(학과 매핑)는 손대지 않는다. 삭제·변경은 공지 단위(`NoticeDetails`) 상태이고, 알림만 학과별 `Notice` 단위로 나간다(기존과 동일).

### 5.2 감지 스케줄러 — 기존 크롤러와 분리한 `NoticeChangeScheduler`

기존 10분 크롤러에 상세 페이지 조회를 끼워 넣지 않는다. 이유: 10분마다 27개 학과 × 수십 건의 상세 페이지를 여는 것은 학교 서버 부하와 기존 크롤러의 10초 타임아웃(`notice.crawl.timeout`) 양쪽에 무리다.

- 주기: **매시 정각(설정값)**, 기존 크롤러와 겹치지 않게 분 오프셋을 둔다(예: `0 5 8-20 * * MON-FRI`). 주말은 학교가 공지를 손대는 일이 드물어 제외하되 설정으로 켤 수 있게 한다.
- 대상: `deleted_at IS NULL AND created_at >= 오늘 - 14일` (일수는 설정값). 학교 공지 정정은 게시 후 며칠 안에 일어나는 것이 대부분이고, 14일 밖의 공지까지 매시간 여는 것은 비용 대비 효과가 낮다.
  추가로 `deleted_at IS NOT NULL AND deleted_at >= 오늘 - 7일`도 포함해 삭제가 되돌려진 경우(복구)를 잡는다(5.6절).
- 단위: **`NoticeDetails` 1건당 상세 페이지 1회 요청**. 대학 공지가 여러 학과에 매핑돼 있어도 details는 하나이므로 중복 요청이 없다.
- 예상 요청량: 학과 27개, 14일치 공지를 학과당 10~30건으로 잡으면 주기당 약 300~800건. 스레드 2~4개, 요청 간 딜레이 200ms 정도면 주기당 1~3분 안에 끝난다. 부하가 문제면 스레드 수·딜레이·창 일수를 yml에서 조정한다.
- 트랜잭션: 네트워크 요청은 트랜잭션 밖에서 수행하고, 판정 결과 저장만 건별 짧은 트랜잭션으로 한다. 기존 `scheduled()`처럼 메서드 전체를 `@Transactional`로 감싸지 않는다(커넥션을 몇 분씩 붙잡게 됨).
- 수동 트리거: 기존 `POST /notice` 패턴을 따라 `POST /notice/change-check` (ADMIN)를 추가한다.

### 5.3 판정 규칙

상세 페이지 응답을 아래 네 가지로 분류하고, **삭제로 판정하는 경로는 하나뿐**이다.

| 응답 | 분류 | 처리 |
|---|---|---|
| 타임아웃, 연결 실패, 5xx, 4xx | 조회 실패 | 아무것도 바꾸지 않는다. 다음 주기에 재시도. **절대 삭제로 보지 않는다** |
| 200 + "원하시는 페이지를 찾을 수가 없습니다" 문구 (또는 `<title>알림메세지</title>`) | 삭제 후보 | `delete_suspect_count += 1`. 설정값(기본 2) 이상이면 삭제 확정 → `deleted_at` 기록, 알림 발송(5.4절) |
| 200 + `.view-sj`와 `.view-con` 모두 존재 | 정상 | 해시 계산 후 아래 "변경 판정". `delete_suspect_count = 0` |
| 200 인데 위 둘 다 아님 (로그인 페이지, 점검 페이지, 마크업 개편 등) | 판정 불가 | 아무것도 바꾸지 않는다. 경고 로그. 한 주기에 이 비율이 임계치(예: 30%)를 넘으면 사이트 구조 변경으로 보고 해당 주기의 모든 변경·삭제 처리를 중단한다 |

**변경 판정 (정상 응답일 때)**
- 해시 입력: `normalize(제목) + "\n" + normalize(본문 텍스트) + "\n" + 첨부파일명들(정렬)`.
- `normalize`: HTML 태그·스크립트 제거 → 텍스트만, 연속 공백 1칸으로 압축, 앞뒤 공백 제거, 제목 끝의 "단축URL복사" 같은 UI 텍스트 제거. **이미지 URL·조회수 같은 동적 값은 입력에 넣지 않는다** — 이걸 넣으면 매시간 "변경"으로 오판한다.
- `content_hash`가 null(첫 조회): **해시만 저장하고 알림을 보내지 않는다(베이스라인).** 이 규칙이 없으면 배포 직후 14일치 공지 전부가 "수정됨"으로 발송된다.
- 해시가 다르다: 변경 확정 → `content_hash`, `modified_at` 갱신, 제목이 바뀌었으면 `title`도 갱신, 알림 발송.
- 해시가 같다: `content_checked_at`만 갱신.

**제목 변경의 빠른 경로 (선택, 권장)**
기존 10분 크롤러가 이미 목록 페이지 15행을 다 읽고 있다. 지금은 신규만 남기고 버리는 나머지 행의 제목을 DB 제목과 비교하면, 제목 변경은 상세 페이지 없이 10분 안에 잡힌다. 이 경우 `modified_at`·`title`을 갱신하고 알림을 보내며, 다음 시간 주기의 해시 비교에서 같은 변경으로 또 알림이 나가지 않도록 쿨다운(5.4절)이 막아준다. 기존 크롤러 코드 변경은 필터 한 줄 뒤에 비교 로직을 붙이는 정도다.

### 5.4 알림

- **타입**: 기존 `NotificationType.NOTICE` 재사용. 새 enum 값을 추가하면 앱이 모르는 타입을 받아 처리 못 할 수 있고, `NotificationSetting` 기본값·설정 화면까지 번진다. 수정/삭제 알림을 따로 끄고 싶다는 요구가 생기면 그때 타입을 분리한다.
- **제목/본문**
  - 수정: 제목 `[학과명] 공지 수정 알림`, 본문 = 새 공지 제목. 제목이 바뀐 경우 본문을 `"이전 제목" → "새 제목"` 형식으로 해 무엇이 바뀌었는지 보이게 한다(길이 제한은 기존 발송 로직의 제한을 따른다).
  - 삭제: 제목 `[학과명] 공지 삭제 알림`, 본문 = 공지 제목.
- **링크(`value`)**: 기존과 같이 학교 상세 URL. 삭제 알림의 링크는 학교 에러 페이지로 가지만, 앱 딥링크 체계를 바꾸지 않는 선에서는 이것이 최선이다. 앱에서 "삭제 알림은 링크를 열지 않는다"로 처리할지는 앱 팀 결정 사항(7절).
- **대상**: 원 공지와 동일하게 `NoticeNotificationImpl`의 흐름을 재사용한다 — 학과 구독 기기 조회 → 회원은 키워드 필터 → 알림함 저장+푸시, 비회원은 푸시만.
  키워드 필터 기준 문자열은 수정의 경우 **이전 제목과 새 제목 중 하나라도** 매칭되면 대상에 넣는다(제목이 바뀌어 키워드가 빠진 사람도 "바뀌었다"는 건 알아야 한다).
  구현은 `NoticeNotificationImpl.send`의 제목 생성·본문 생성 부분을 파라미터화(알림 종류 enum: NEW/UPDATED/DELETED)해 재사용한다. 발송 파이프라인을 복제하지 않는다.
- **중복·폭주 억제**
  - 같은 공지의 수정 알림은 **24시간(설정값)에 1회**. `modified_at`이 쿨다운 안이면 DB 갱신만 하고 발송은 건너뛴다.
  - 삭제 알림은 공지당 1회(`deleted_at`이 이미 있으면 발송하지 않음).
  - 한 주기에 발송 가능한 수정+삭제 알림 총량 상한(설정값, 예: 50건). 넘으면 나머지는 DB 갱신만 하고 경고 로그. 학교 사이트 마크업 개편 같은 사고로 전 사용자에게 수백 건이 나가는 것을 막는 마지막 안전장치다.

### 5.5 목록·홈·검색 반영

- 아래 조회에 `noticeDetails.deletedAt IS NULL` 조건을 추가한다.
  - `NoticeRepository.findAllByDepartment`, `findAllByDepartmentIn` (앱 공지 목록, 비회원 통합 목록)
  - `NoticeRepositoryCustomImpl.searchHomeNotices` 외 홈 쿼리 3개
- **`getNoticeRecentIdMap`(학과별 최신 글번호)은 삭제 여부와 무관하게 전체에서 MAX를 구해야 한다.** 삭제된 글을 제외하면 최신 번호가 뒤로 밀려, 다음 크롤에서 이미 저장된 공지를 다시 신규로 판정해 중복 저장·중복 알림이 난다. 이 쿼리는 건드리지 않는다.
- `NoticeListResponse`에 `modifiedAt`을 추가한다(nullable). 앱이 "수정됨" 배지를 붙일지는 선택이며, 필드 추가만으로는 앱이 깨지지 않는다.
- 삭제된 공지는 **물리 삭제하지 않는다.** 알림함(`NotificationDetails.value`)이 링크를 들고 있고, 복구(5.6절) 시 되살려야 하며, 최신 글번호 계산에도 필요하다.
- **검색(Elasticsearch)**: 이 레포는 `BoardDocument`를 색인하지 않는다(읽기만 한다). 색인은 외부 파이프라인이 DB를 읽어 만들므로, 그 파이프라인에 `deleted_at IS NULL` 필터를 추가해야 삭제 공지가 검색에서 빠진다. **이 레포 밖의 작업이며 별도 추적이 필요하다.**

### 5.6 복구(삭제 후 재등장)

삭제 확정된 공지가 7일 이내 다시 정상 응답을 주면(학교가 실수로 지웠다 복원, 또는 4.4의 가정이 틀린 경우) `deleted_at`을 null로 되돌리고 `delete_suspect_count`를 0으로 리셋한다. 알림은 보내지 않고 경고 로그만 남긴다 — 복구 알림까지 보내면 삭제→복구 왕복마다 두 번씩 울린다. 이 로그가 자주 찍히면 4.4의 삭제 판정 가정을 재검토해야 한다는 신호다.

### 5.8 운영·배포 시 신경 쓸 것

1. **첫 실행 부하**: 배포 직후 첫 주기에 14일치 공지 전부의 상세 페이지를 열어 베이스라인을 잡는다(수백 건). 트래픽이 적은 시간대에 배포하거나 `enabled: false`로 배포 후 수동 트리거로 첫 실행을 한다.
2. **이중 실행 방지**: 공지 크롤러가 별도 인스턴스에서 돈다면 이 스케줄러도 **그 인스턴스에서만** 돌아야 한다. 현재 `@Scheduled`에 프로파일 게이트가 없으므로, 기존 크롤러가 어떻게 한 인스턴스에서만 돌게 하고 있는지(프로파일/인스턴스 수) 같은 방식을 따른다. 두 인스턴스에서 동시에 돌면 알림이 두 번 나간다.
3. **학교 서버 매너**: 기존 user-agent(`NoticeBot/1.0`) 유지, 딜레이 준수, 연속 5xx 시 해당 주기 중단. 차단당하면 신규 공지 크롤링까지 같이 죽는다.
4. **롤백**: 컬럼은 nullable이라 코드만 되돌려도 동작한다. `deleted_at`이 남아 있어도 이전 코드는 그 컬럼을 모르므로 목록에 다시 나타날 뿐 장애는 아니다.
5. **로그·지표**: 주기별로 확인 건수, 정상/변경/삭제후보/삭제확정/실패/판정불가 건수, 발송 건수를 한 줄로 남긴다. 첫 1~2주는 "변경" 판정이 실제 정정인지 표본 확인한다(동적 요소 오판 점검).

### 5.9 엣지 케이스 정리

| 상황 | 동작 |
|---|---|
| 학교 사이트 전체 장애 | 전부 조회 실패 → 아무 변경 없음. 삭제 오판 없음 |
| 점검 페이지·로그인 리다이렉트가 200으로 옴 | 판정 불가 → 무시. 비율 임계치 넘으면 주기 중단 |
| 사이트 마크업 개편으로 선택자 전멸 | 전부 판정 불가 → 아무것도 안 함(안전). 기존 크롤러도 같이 깨지므로 어차피 대응 필요 |
| 본문에 조회수·오늘 날짜 등 동적 텍스트 | 해시 입력에서 `.view-con` 텍스트만 쓰고 배포 후 표본 확인. 반복 오판되는 패턴은 normalize에 제거 규칙 추가 |
| "[정정]" 제목의 새 공지 | 별개의 신규 공지로 기존 흐름 처리. 원 공지와 연결하지 않는다 |
| 대학 공지(여러 학과 매핑) | 상세 조회 1회, 알림은 학과별 `Notice`마다(기존과 동일) |
| 삭제 후보 1회 관측 후 정상 응답 | 카운트 0으로 리셋. 알림 없음 |
| 한 시간 안에 여러 번 수정 | 다음 주기에 한 번만 감지되고 한 번만 알림 |
| 제목 빠른 경로(10분)와 시간 주기 해시가 같은 변경을 각각 감지 | 쿨다운 24시간으로 두 번째 발송 차단 |
| 크롤 타임아웃으로 부분 결과 저장 중 스케줄러 겹침 | 두 스케줄러는 서로 다른 컬럼만 쓰고(신규 삽입 vs 상태 갱신) 같은 행을 동시에 만지지 않으므로 충돌 없음. 단 `getNoticeRecentIdMap`이 삭제를 포함해야 한다는 5.5절 조건은 여기서도 전제 |

### 5.11 테스트 계획

기존 `NoticeCrawlingTest`, `NoticeNotificationTargetingTest`의 방식(슬라이스 `@SpringBootTest` + `@MockitoBean`, HTML 픽스처)을 따른다.

- 응답 4분류 판정: 정상 HTML / 에러 안내 HTML / 선택자 없는 HTML / 예외 → 각각 기대 분류
- 해시 정규화: 공백·줄바꿈·"단축URL복사" 차이만 있는 두 HTML은 같은 해시, 본문 한 글자 차이는 다른 해시, 첨부 순서만 달라도 같은 해시
- 베이스라인: `content_hash` null인 공지는 해시 저장만 되고 알림 호출 0회
- 삭제 확정: 후보 1회는 미확정, 2회 연속이면 확정 + 알림 1회, 중간에 정상 응답이 끼면 카운트 리셋
- 복구: 확정 후 정상 응답이면 `deleted_at` null, 알림 0회
- 쿨다운: 24시간 내 두 번째 변경은 DB 갱신만
- 총량 상한: 상한 초과분은 발송되지 않음
- 판정 불가 비율 초과 시 해당 주기에 변경·삭제 처리 0건
- 목록 쿼리: `deleted_at`이 있는 공지는 목록·홈에서 제외되고, `getNoticeRecentIdMap`에는 포함됨(통합 테스트, Testcontainers)
- 알림 대상: 제목 변경 시 이전 제목 키워드 보유자와 새 제목 키워드 보유자 모두 포함

## 7. 결정이 필요한 항목

1. **삭제 알림을 보낼지.** 요청대로 보내는 것으로 설계했지만, 수정 알림보다 노이즈가 될 가능성이 있다. 대안은 목록에서만 내리고 알림은 수정에만 보내는 것.
2. **재확인 창 14일**이 적절한지. 학교 공지 정정 패턴을 아시면 조정한다.
3. **앱 측 대응 범위**: 삭제 알림 탭 시 링크를 열지 여부, `modifiedAt` 배지 표시 여부. 백엔드는 둘 다 없이도 동작한다.
4. **검색 인덱스 파이프라인**의 `deleted_at` 필터를 누가 언제 넣을지(이 레포 밖).
5. **크롤러 인스턴스 배치**: 감지 스케줄러를 기존 크롤러와 같은 인스턴스에서만 돌리는 방법 확인(5.8-2).
